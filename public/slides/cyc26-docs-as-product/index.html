Documentation in the Age of AI

Why We Should View Docs as a Product

Target duration: 0:45

Thesis: AI does not make documentation less important. It makes documentation quality more consequential.

Delivery: AI does not make documentation less important. It gives people another path through the same source material, which makes accuracy, ownership, and maintenance more consequential. My argument is simple: documentation should be managed with the same product discipline as the experience it supports.

Who reads your docs?

And what counts as “reading”?

Target duration: 0:35

Thesis: A product view begins by naming the user and the job, rather than treating every request, visit, fetch, or answer as the same event.

Delivery: Start with the obvious reader: a person trying to understand or use the product. Today, that person may read the page directly or ask an agent that consults the page for them. Both paths begin with the same question: what is the user trying to do?

The wider web

Target duration: 1:05

Fact: Thales reported that bots accounted for 53% of the web traffic in its full-year 2025 analysis, while human traffic accounted for 47%. In a separate 2025 measurement across its customer base, Cloudflare found that identified AI bots averaged 4.2% of HTML requests and broke out dual-purpose Googlebot separately at 4.5%.

Delivery: Before we narrow the lens to documentation, look at the wider web. In Thales's analysis of 2025 traffic, automated requests exceeded human traffic: 53% to 47%. That 53% includes bots in aggregate, not just LLM crawlers or agents. Cloudflare's separate HTML-request analysis makes the distinction concrete: identified AI bots averaged 4.2%, with dual-purpose Googlebot counted separately at 4.5%. So the broad evidence supports a bot majority, not an AI majority. The next two measurements narrow the lens to documentation platforms and classify agent requests separately.

Docs traffic · GitBook

Target duration: 1:10

Fact: In a one-week GitBook sample, AI-agent requests were 51.8% of requests GitBook classified as intentional reads; human requests were 48.2% within that same constructed denominator.

Delivery: GitBook classified platform page requests into human, AI-agent, crawler, and other-bot categories. It then excluded the crawler categories and published this split for what it called “intentional reads.” In that one-week sample, AI-agent requests narrowly exceeded human requests. The unit is a page request, not a person, session, completed task, or comprehension event. The evidence is bounded, but it is enough to show that the old mental model is incomplete.

Fact: In Mintlify's July 2026 report, agent web requests were 213 million versus 105 million human page loads across Mintlify-hosted documentation, a reported 66% agent share, up from 15.2% at the start of the year.

Delivery: Mintlify's midyear report counted 213 million agent HTTP requests and 105 million human browser page loads in July. These are different event types: human activity is measured through client-side page loads, while agent activity is measured through server-side requests. The GitBook and Mintlify methods also differ, so the two slides should not be combined into one trend.

Why quality matters

Bad docs become bad actions.

The agent follows the wrong path. The task fails. The user feels the frustration.

Target duration: 1:15

Thesis: When agents use documentation to act, unclear or incorrect guidance becomes a failed user task, not merely a confusing page.

Delivery: A person can sometimes notice that a page is incomplete and work around it. An agent may confidently follow the documented path. If that guidance is wrong, stale, or missing a critical constraint, the action fails and the user experiences the frustration. That is why documentation quality and ownership now have direct product consequences.

What that looks like in practice.

  2. 02 Build it fast Low-friction drafting: agentic tooling, human in the loop
  3. 03 Keep it correct Automated checks in CI (spectral for OpenAPI) before publish
  4. 04 Make it reachable llms.txt, MCP, and pages you can copy as Markdown (.md)
  5. 05 Learn and improve Analytics, user feedback, and a maintenance roadmap

Target duration: 0:50

Thesis: Treating documentation as a product is an operating model, not a slogan. These five pillars are what the discipline actually looks like, and each one gets its own moment in the slides that follow.

Delivery: If bad docs now become bad actions, docs deserve the same investment as any product. That means five things: someone owns the system while the feature teams own the truth; we build drafts fast and low-friction with a human in the loop; we keep content correct with automated checks in CI; we make it reachable to people and agents alike; and we learn from real use and improve. The next few slides walk each one.

Docs as product

The system and content need different owners.

Docs product owner Owns the system Infrastructure, publishing, agentic authoring tools, discovery, and usability
Feature PMs + engineers Own the content Accuracy, initial drafts, and maintenance as the product changes

Target duration: 1:10

Recommendation: Separate ownership of the documentation system from ownership of the product truth expressed in each document.

Delivery: The docs product owner maintains the infrastructure, publishing workflow, authoring and agent tooling, and the paths that make documentation discoverable and usable. PMs and engineers own the feature content itself: they create or verify the initial draft, ensure it is accurate, and keep it current as the product changes.

Docs as product

Start with a user and a task.

Then measure whether they can complete it.

A request ≠ A completed task

The same task must succeed for a human and an agent.

Target duration: 2:15

Thesis: Manage documentation as a product: name the user and the task, then measure whether that task can actually be completed. Traffic is a signal; task completion is the outcome that matters.

Delivery: “Developers” is not a user model. An evaluator choosing a product, an operator responding to an incident, and an integrator handling a breaking change have different jobs. Name the user, name the task, and define what successful completion looks like. Then measure it: traffic tells us a request reached a page, not whether the user found the right version, understood the constraint, or completed the task. Test a specific job with a person or agent, observe what happens, and connect the result to a decision: improve navigation, clarify a prerequisite, or retire a stale example.

A practical workflow

Use AI to draft, not to decide.

AI tools Draft
Truth owners Review
CI checks Validate
Docs system Publish
Truth owners Maintain

Target duration: 0:50

Recommendation: Use AI to accelerate the first draft while keeping review and maintenance with the PMs and engineers who own the product truth.

Delivery: AI tools can turn product context into an initial draft. The PMs and engineers closest to the feature review what is true, automated checks in CI validate the change (spectral linting on OpenAPI, for example), then the docs system publishes the approved version, and those same truth owners maintain the content as the product changes. The docs product owner maintains the infrastructure and tooling that make this workflow possible.

Human and agent access

Keep one source of truth. Serve every reader.

For people Usable site docs Browse, search, ask AI, and view or copy pages as Markdown.
Source of truth Canonical documentation Versioned, reviewed, maintained, with changelogs.
For agents Useful access paths llms.txt · llms-full.txt · .md pages · MCP tools

Target duration: 1:15

Recommendation: Keep the primary documentation site readable and useful for people, then offer machine-oriented representations or interfaces from that same governed source when a named task justifies them.

Delivery: Keep one maintained source of truth, then offer it in forms that fit the job. People need readable pages and may want to copy a page as Markdown. Agents may use a curated llms dot txt, a synchronized full export, or MCP tools when interaction is required. These are access paths, not separate documentation systems.

Docs as product

Let real use shape the roadmap.

Measure Watch the signals Top searches, and whether AI chats actually answer, or come up empty
Listen Act on feedback Capture it and ship it, crediting the community
Improve Plan the work A maintenance roadmap that keeps every task doable, for agents and people

Target duration: 1:10

Thesis: A product listens to how it is used and improves on purpose. Documentation should do the same, turning real signals into a maintained roadmap.

Delivery: Measure what people and agents actually do: which topics get searched most, and whether the AI answers those questions or comes up empty. Listen to feedback, act on it, and credit the community as a whole rather than calling out individuals. Then improve deliberately: keep a maintenance roadmap that plans the work and keeps each task completable by both an agent and a person. That loop is what makes docs a product instead of a static artifact.
